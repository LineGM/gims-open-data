# Публичный протокол тренажёра ГИМС МЧС

Дата наблюдений: **12 сентября 2026 года**, примерно 07:20–07:26 UTC.
Единственный источник данных: [официальный тренажёр МЧС](https://digital.mchs.gov.ru/gims/simulator) и ресурсы, загруженные его публичным клиентом.

**Результат:** марафон доступен без входа через ЕСИА. Создание — HTML-форма с сессионной cookie и CSRF-токеном; переходы — публичный JSON API. Обычный HTTP-клиент воспроизвёл создание и два перехода в новой сессии без браузера. В JSON есть серверный UUID вопроса. Для вопросов № 2 и № 3 он совпал между двумя независимыми марафонами.

Это описание наблюдаемого клиентского протокола, а не гарантированная сервером спецификация. Ниже отдельно обозначены проверенные факты, выводы из JS и неизвестные детали.

## 1. Объём и условия исследования

- Playwright MCP: один марафон A, два правильных ответа, просмотр вопросов № 1–3.
- Python `urllib.request`: второй марафон B с новой `CookieJar`, два правильных ответа, получение вопросов № 1–3. Параметры создания совпали с A.
- Всего **четыре отправки ответов**, по две на марафон. Вопрос № 3 в обоих марафонах оставлен без ответа.
- Дополнительно создался один `fixed`-экзамен: первоначальный клик по radio перекрывала его label, переключение не состоялось. В нём просмотрена первая страница, ответов и переходов не было. После этого режим выбирался через label и проверялся до отправки.
- Все исследовательские обращения выполнялись последовательно, без массового сбора и повторного обхода базы. Браузер также штатно загружал CSS, JS, шрифты и изображения страницы.
- HTTP-ответов 403/429/5xx не наблюдалось. Первый запуск локальной HTTP-проверки остановился на запрете сокета песочницей (`WinError 10013`), до HTTP-ответа; повторный запуск с разрешённым сетевым доступом прошёл успешно.
- Не выполнялись вход, обход CAPTCHA, запросы административных API, перебор идентификаторов, пропуски вопросов и завершение теста.

Материалы наблюдений: [fixtures](../research/fixtures/README.md). Instance, коды активации, стартовые UUID, cookie и CSRF заменены маркерами. UUID вопросов и ответов оставлены без изменений как публичные идентификаторы содержимого.

## 2. Архитектура

На `digital.mchs.gov.ru` есть страница выбора `/gims/simulator` и подсистема тестирования под `/testing`. Начальная страница вопроса рендерится сервером. Затем JS перехватывает submit формы, вызывает `/testing/api/instance/{instance_uuid}` и обновляет отдельные элементы DOM без навигации.

Заголовки подсистемы тестирования содержали `server: nginx` и `x-powered-by: PHP/8.3.33`. HTML-форма с именем `gims_simulator_form` похожа на Symfony Form, но конкретный серверный фреймворк исследованием не установлен. Браузерный клиент использует jQuery, Select2 и webpack bundles.

Изображения выдаются тем же hostname по **HTTPS на порту 85**, из `/testing_bucket/`. Заголовок `x-amz-request-id` совместим с объектным хранилищем, но конкретное ПО хранилища не установлено.

В случайно созданном экзамене с шестью типами судов и тремя районами было `1/35`, `data-mode="simulator"`, таймер около 45 минут и кнопка «Ответить позже». Экзаменационный алгоритм дальше не исследовался. Других доступных настроек создания в форме не найдено.

## 4. Последовательность запросов

```text
GET  /gims/simulator
  -> 200 HTML: форма, CSRF; клиент сохраняет PHPSESSID
POST /gims/simulator  (application/x-www-form-urlencoded)
  -> 302 Location: https://digital.mchs.gov.ru/testing/activate/{activation_code}
GET  /testing/activate/{activation_code}
  -> 302 Location: /testing/test/{test_uuid}/start/{start_uuid}
GET  /testing/test/{test_uuid}/start/{start_uuid}
  -> 302 Location: /testing/instance/{instance_uuid}
GET  /testing/instance/{instance_uuid}
  -> 200 text/html; charset=UTF-8: первый вопрос
UI «Ответить»
  -> только локальная проверка и подсветка, без HTTP
UI «Следующий вопрос»
POST /testing/api/instance/{instance_uuid}  (application/json)
  -> 200 application/json: следующий вопрос и новое состояние
```

Тело создания, с обезличенным токеном:

```text
gims_simulator_form%5Btype%5D=marathon&gims_simulator_form%5Bsend%5D=&gims_simulator_form%5B_token%5D=REDACTED_CSRF_TOKEN
```

Коды активации имели вид `T` и девять цифр; это форма наблюдаемых значений, а не установленная регулярная грамматика. UUID в `/test/.../start/...` выдаёт сервер. Назначение первого UUID предположительно связано с шаблоном теста; это **не question ID**. Второй UUID, activation code и instance UUID различались при создании. Использовать нужно `Location`, а не конструировать эти значения.

Тела ответов-редиректов не сохранены; в fixtures есть статусы и значимые заголовки. Конечный ответ создания — HTML. При AJAX-переходе редиректа нет, адрес страницы остаётся `/testing/instance/{instance_uuid}`.

## 6. Cookie, сессия и CSRF

Наблюдалась одна cookie: `PHPSESSID`, domain `digital.mchs.gov.ru`, path `/`, `Secure`, `HttpOnly`, `SameSite=Lax`, сессионная, без постоянного срока жизни. Значение не сохранено. В новой HTTP-сессии сервер также установил эту cookie; существующую браузерную сессию в Python не переносили.

Для создания передавался `gims_simulator_form[_token]`, прочитанный из того же GET и в той же cookie-сессии. Отправка без токена специально не проверялась: наличие CSRF-поля установлено, точная серверная проверка не тестировалась.

JSON POST ответа содержит только `answer`; отдельного CSRF-поля, Authorization или CSRF-заголовка в нём нет. Браузер посылал cookie, `Origin`, `Referer`, `Accept: */*`, `Content-Type: application/json` и стандартные браузерные заголовки. Чистый Python-клиент успешно отправил ответы с cookie и JSON Content-Type, без браузерных `Origin`/`Referer` и без подмены User-Agent.

Работа без cookie не проверялась; это не основание считать её необязательной. На страницах марафона `localStorage` и `sessionStorage` были пустыми; inline JSON state не найден. В DOM есть общие скрытые элементы проверки устройств, но `#capture-settings` отсутствует: прокторинг не был частью исследованного марафона.

Парсер должен учитывать различие начального HTML и последующего JSON.

## 8. Отправка ответа и JSON-контракт

Подтверждённое тело правильного ответа на первый вопрос:

```json
{"answer":"95902c7d-14ea-4950-a64c-044dece028a4"}
```

Сервер определяет текущий вопрос по состоянию instance; в проверенном ответе клиент не отправляет номер вопроса, его UUID или UUID следующего вопроса. Ответ содержит **следующий** вопрос, не отдельный объект результата предыдущего.

| Поле JSON | Наблюдаемое содержание |
| --- | --- |
| `id` | UUID instance |
| `current_question.id` | Серверный UUID вопроса |
| `current_question.content` | Текст вопроса |
| `current_question.resources_path` | Массив URL изображений |
| `current_question.type` | `single` в проверенных ответах |
| `current_question.is_additional` | `false` |
| `current_answers[]` | Объекты `{id, title, resources_path}` |
| `questions_count` | `1513` |
| `question_number` | Число `2`, затем `3` |
| `questions_passed` | `1`, затем `2` |
| `questions_statuses` | Пустой массив в проверенных ответах марафона |
| `valid_answer` | UUID правильного ответа для следующего single-вопроса |
| `valid_answers` | Строка правильных UUID для следующего вопроса |

После первого нажатия «Ответить» сеть не используется: JS добавляет labels классы `answers-correct` / `answers-wrong` и меняет кнопку на «Следующий вопрос». При втором нажатии отправляется выбранный ответ, возвращается JSON, счётчики обновляются. Дополнительных пояснений, нормативных ссылок, категорий судна/района, редакции вопроса и даты изменения в изученном JSON нет.

В функции `sendAnswer` того же клиента также есть тела `{"skip":true}` и `{"question":"..."}` для других UI-действий, в частности экзамена. Их семантика в марафоне **не проверена**. Ветка JS при отсутствии `current_question` перезагружает страницу; завершение и полный финальный ответ сервера не проверены.

## 9. Правильные и множественные ответы

Начальный single-вопрос: UUID правильного ответа берётся из HTML `data-valid-answers` / `data-valid-answer`, сопоставляется с `input.value`. Для первого вопроса он соответствует «При придании судну небольшого дифферента на корму».

Начиная со второго вопроса источником правильных ответов является `valid_answers` последнего JSON. В изученных ответах `valid_answer` и `valid_answers` совпадают. Не следует переносить это равенство на multiple-вопросы.

**Multiple-вопросы в разрешённой выборке не встретились.** Ни реальная multiple HTML-страница, ни multiple JSON-ответ, ни серверная оценка такого ответа не проверены. По загруженному публичному JS установлено:

- `valid_answers` разбивается через `.split(',')`.
- При следующем вопросе марафона `isMultiple = validAnswers.length > 1`.
- Рендерятся `input type="checkbox" name="answer[]"` с UUID в `id` и `value`.
- Если выбрано несколько inputs, JSON отправляется как `{"answer":["UUID_1","UUID_2"]}`. При одном выбранном input отправляется строка, даже если сам вопрос multiple.
- Локальная подсветка проверяет принадлежность каждого UUID множеству правильных ответов.
- В экзаменационной ветке JS признак multiple читается из `current_question.type === 'multiple'`.

Значение `valid_answer` при multiple, порядок UUID в `valid_answers`, частичный зачёт и обработка неполного набора неизвестны. Синтетический multiple fixture не выдаётся за наблюдаемые данные.

## 10. Изображения

Начальный HTML содержит `img` внутри `[data-name="question-image"]`. JSON содержит массивы `resources_path` как у вопроса, так и у каждого ответа. Во всех трёх просмотренных вопросах было по одному изображению вопроса и текстовые варианты с пустыми массивами ресурсов.

Пример официального URL:

```text
https://digital.mchs.gov.ru:85/testing_bucket/654a4c1d7b794b6eb6b286059ad2b9db-60190c174269e1.00685403.jpeg
```

У этого изображения подтверждены HTTP 200, `Content-Type: image/jpeg`, длина 54788 байт, `ETag`, `Last-Modified`, `Accept-Ranges: bytes`. PNG следующих вопросов также загрузились с HTTP 200. Бинарные изображения в fixtures не сохранялись.

По JS клиент использует только `resources_path[0]`. При пустом массиве удаляет контейнер изображения. Для графического варианта ответа используются `label.answers-image`, `.answers-picture img`, `.answers-overlay`; это подтверждено кодом, но реальный такой вариант в выборке не встретился. Будущий формат данных должен сохранять весь массив ресурсов, а не только показанный в UI первый файл.

Имя файла, `ETag` и `x-amz-request-id` нельзя считать question ID: первое идентифицирует ресурс неустановленным способом, второе относится к объекту/версии, третье к запросу. Соответствие одному вопросу или устойчивость этих значений не доказаны.

## 11. Question ID и стабильность UUID

**Явный question ID есть в JSON: `current_question.id`.**

| Позиция | Серверный question UUID | Результат сравнения A/B |
| --- | --- | --- |
| 1 | Не обнаружен в начальном HTML | Совпали порядок и четыре UUID вариантов, правильный UUID; вопрос A соответствует известному ручному примеру |
| 2 | `26115699-40f6-4cdc-bcf2-4e411509b7d8` | Весь JSON совпал, кроме `id` instance |
| 3 | `de566241-be55-40b1-888e-95c30932ef5e` | Весь JSON совпал, кроме `id` instance |

Сравнение полных JSON для № 2–3 включает текст, question UUID, порядок массива ответов, UUID/тексты ответов, правильные ответы, изображения, счётчики и flags. Оно выполнено локально программным сравнением.

Это подтверждает стабильность question UUID для двух вопросов и answer UUID первых трёх позиций **между двумя свежими сессиями в один день**. Устойчивость после обновления официальной базы, на остальных позициях и между экзаменационными конфигурациями не проверена.

Первые три позиции марафонов согласуются с одинаковым порядком вопросов, но порядок всего корпуса не доказан. Порядок вариантов нужно различать: первый raw HTML в A/B имел одинаковый порядок; массивы JSON № 2–3 также совпали, однако браузерный JS вызывает `shuffle(answers)` перед отображением следующих вопросов. DOM-порядок вариантов № 2 действительно отличался от порядка в JSON.

**Открытый вопрос: как получить официальный UUID самого первого вопроса.** В его raw HTML, атрибутах, формах, inline state и заголовках такого UUID нет. После ответа JSON уже описывает второй вопрос. Отдельный публичный способ прочитать текущий вопрос как JSON до первого ответа пока не установлен. Собственная схема идентификаторов не вводилась.

## 12. HTTP-клиент и будущий httpx

Практически подтверждён полный путь **GET формы → создание → три редиректа → HTML → два JSON POST** без Playwright. Проверка выполнена стандартным `urllib.request`, с новым cookie jar, стандартной проверкой TLS и обычным Python User-Agent. Изображения, скрипты и стили HTTP-клиент не загружал. Зафиксированы семь последовательных HTTP-запросов; каждый прикладной запрос начинался с паузой в одну секунду.

В окружении пакет `httpx` не установлен, поэтому именно эта библиотека не запускалась. Возможность будущей реализации на `httpx.Client` — обоснованный вывод из успешного обычного HTTP-обмена: нужны сохранение cookies, URL-encoded POST, разбор HTML, обработка `Location` и JSON POST. Выполнение JavaScript для проверенного пути не требуется.

Рекомендуется вручную контролировать редиректы и проверять статус каждого ответа: при 403/429/5xx прекращать работу до следующего запроса. Отправку ответа нельзя безусловно повторять после таймаута: это меняющая серверное состояние операция. Срок жизни instance, повторные GET и способ согласования состояния после прерывания ещё не проверены.

## 13. Риски и неизвестные детали

1. Не найден способ получить question UUID первой позиции; нельзя незаметно пропустить её в будущем corpus.
2. Количество 1513 не подтверждает уникальность, неизменность или охват всех официальных вопросов. Привязки к типам судов и районам в JSON марафона нет.
3. Multiple-вопросы, варианты-картинки, вопросы без картинки и с несколькими ресурсами изучены только по клиентскому коду там, где он содержит соответствующие ветки.
4. Не исследованы ошибки ответа, повторное появление неверно решённых вопросов, дополнительные вопросы, пропуск, завершение и восстановление после прерывания.
5. Нет проверки сохранности UUID во времени. Порядок вариантов в браузере перемешивается; порядок всего марафона может измениться.
6. DOM `data-valid-*` устаревает после первого перехода. Номер в DOM меняет формат с `1/1513` на число без знаменателя.
7. Публичный протокол может изменяться без версии и предупреждения. Значимые ответы имеют `Cache-Control: max-age=0, must-revalidate, private`; question-specific `ETag`/revision в них не найдено.
8. Порт 85 изображений может быть недоступен в отдельных окружениях. Доступ к изображениям обычным HTTP-клиентом отдельно не проверялся.
9. Ограничения частоты, срок жизни сессии, обязательность cookie и серверная CSRF-валидация не измерялись. Нагрузочных проверок не было.
10. В подвале официального сайта указана Creative Commons Attribution 4.0, но применимость и оформление атрибуции для распространяемого набора вопросов и изображений нужно отдельно зафиксировать перед публикацией corpus. Это исследование не является юридическим заключением.

## 14. Следующие шаги для воспроизводимого сбора

1. Сделать **офлайн-парсер начального HTML и JSON**, с тестами на приложенных fixtures: извлечение текста, UUID, правильных ответов, всех ресурсов и counters. Учесть устаревающие DOM-атрибуты и различие номера/общего количества.
2. Отдельным небольшим исследованием закрыть получение официального ID первого вопроса, реальный multiple-вопрос и графические варианты. Использовать только публичный клиентский протокол и заранее ограниченный бюджет обращений.
3. Проверить на малой выборке повторный GET текущего instance и восстановление после остановки; определить политику недопущения повторного изменяющего POST.
4. До массового запуска согласовать условия сбора: атрибуция, частота запросов, критерии остановки, дата версии источника и ожидаемый охват.
5. После этого реализовать последовательный импортёр на `httpx` с журналом состояния, сохранением исходных ответов без токенов/cookies, контролем схемы и итоговой проверкой полноты/дубликатов. Идентификаторами должны служить проверенные серверные question UUID; нерешённый первый ID нельзя заменять молча.
6. Для воспроизводимости будущего релиза сохранять manifest с временем получения, параметрами, версиями парсера/схемы, исходными публичными URL, числом позиций и уникальных вопросов, контрольными суммами артефактов и ресурсов. Контрольные суммы артефактов не объявлять новой схемой question ID.

На этом этапе импортёр, массовый scraper, Flutter-приложение и полный corpus **не создавались**. Одноразовый сетевой probe удалён после сохранения обезличенных результатов.
